# H3 / Qwen Image live generation and VRAM audit

Date: 2026-09-24. Hardware: RTX 3090, 24 GiB VRAM, 64 GiB RAM,
Windows, NVIDIA driver 610.74. Device memory below includes the desktop and
other GPU processes; PyTorch allocator statistics are reported separately.

Qwen used Torch 2.11.0+cu130, Diffusers 0.41.0.dev0 at
`6256aa7666cedd47443adc8f82da9a10e110b09c`, Transformers 5.17.0,
Accelerate 1.15.0, bitsandbytes 0.50.2 and gguf 0.19.0. The regular GGUF
revision was `2c31ccd392b367a6637841a143813320a02dff55`.
H3 used Torch 2.11.0+cu130, comfy-kitchen 0.2.35 and comfy-aimdo 0.5.5,
with the installed INT8 FL2VA model and compiler disabled. All generation runs
were sequential; each worker/backend was released before the next began.

## Changes

- Qwen: enable 512 px VAE tiles with 256 px stride above 1280 × 1024 output
  pixels. Disable it again
  when a reused pipeline returns to a smaller output. Record `vae_tiling` in
  result metadata. This reduces decode memory; it does not cap transformer
  attention memory or guarantee that arbitrary reference-image batches fit.
- Qwen: before rewriting/loading a BF16 GPU-resident job, compare local
  safetensors index weight sizes with physical GPU capacity. Single-file
  Turbo weights are counted from their header, accounting for BF16 conversion
  without reading tensor payloads. The installed
  regular transformer and text encoder alone require 29.58 GiB, so 24 GiB
  cannot hold them together. Reject that configuration with an offload or
  quantization alternative. Offload remains available. This lower-bound
  check does not certify configurations that pass it; VAE/activations and
  other processes still consume memory.
- H3: dynamic-VRAM profiles request 2 GiB of extra headroom, in addition to
  the existing model-loading reserve. Runtime recognition rejects the old
  no-headroom command so it cannot silently reuse a backend lacking the new
  setting. The RAM profile disables DynamicVRAM and retains its old command.
  Both 4-step and normal 20-step 5-second generation/decode tests passed.

## Qwen tiling quality comparison

The 256/192 VAE defaults showed visible grid artifacts even at 40 steps.
Three alternatives decoded the **same unpacked, denormalized latent**, so
prompt/seed/sampling differences cannot explain the improvement. All outputs
were 2048 × 2048 RGBA. The red teapot, handle, spout, reflections and pale
background were visually inspected; 512/256 removed the conspicuous grid
without the larger memory cost of 768/512 and was selected.

| Tile / stride (pixels) | Decode peak allocated MiB | Decode peak reserved MiB |
|---|---:|---:|
| 512 / 384 | 2451.3 | 2728 |
| **512 / 256 (selected)** | **2507.1** | **2880** |
| 768 / 512 | 4542.3 | 5384 |

These are allocator measurements around each comparison decode, not whole-job
peaks. The comparison harness resets allocator peaks between candidates;
therefore its ordinary result JSON's final allocator peak must **not** be
interpreted as including model loading. Whole-job device peak 11684 MiB was
sampled independently with NVML. The 784.8-second duration includes comparison
overhead, not just the selected configuration.

The default output is `qwen-job-2048x2048-40steps/output.png`; the selected
candidate is `tile-512-stride-256.png` in that directory. Comparison details
are in `decode-comparison.json`, with saved pre-decode latent for reproduction.
This is a text-to-image test. Tiling also affects reference-image encoding;
multi-reference editing was not revalidated here.

Local evidence: `tmp/live_h3_qwen/` (ignored scratch data), including
`qwen-job/smoke_summary.json`, `bf16-capacity-check.log`, and
`targeted-final.log`. No checkpoint files were deleted.

## Sources and interpretation

- [Diffusers memory guide](https://huggingface.co/docs/diffusers/optimization/memory),
  checked 2026-09-24: VAE tiling reduces decode peaks, with possible tile-to-tile
  tone variation. Outputs need visual inspection.
- [Safetensors format](https://github.com/safetensors/safetensors#format),
  checked 2026-09-24: single-file preflight reads the little-endian header
  length, tensor shapes/dtypes and byte offsets. Regression tests cover the
  single-file Turbo layout and FP32-to-BF16 size conversion; Turbo BF16 live
  generation was not performed.
- Installed Qwen VAE implementation:
  `models/Qwen-Image-2.1/worker-env/Lib/site-packages/diffusers/models/autoencoders/autoencoder_kl_qwenimage21.py`
  (`AutoencoderKLQwenImage21`, confirmed from the installed model config).
- Installed ComfyUI `comfy/cli_args.py` defines `--vram-headroom` as extra
  free memory accounting for other applications; `main.py` passes it to
  `comfy_aimdo.control.init_devices`. It is a model eviction policy, not a hard
  limit on all CUDA allocations.
- Local regular model safetensors indexes: transformer 14,230,249,472 bytes;
  text encoder 17,534,247,392 bytes. BF16 offload only needs one major
  component resident at a time, so these figures do not justify banning it.
- Astra reviewed the DynamicVRAM proposal and BF16 capacity guard. Advice
  was checked against the installed code and model metadata.

No universal OOM-free claim is made. Higher H3 resolutions/durations, Qwen
reference-image batches, and concurrent external GPU applications need
separate measurements.
